# Product media handoff

Selected product stills now enter a durable, asynchronous vision/editing queue. Original uploads remain unchanged; generated images are separate B assets. Results stay suggestions until the owner explicitly chooses them before final review freezes the draft.

## APIs and UI

- A successful draft-bound photo upload/attachment immediately enqueues media and returns `media: { job }`; GET call also includes each draft's `media` projection. Upload does not wait for models or hold the microphone open.
- `GET /api/calls/:id/drafts/:draftId/media` returns `{ job: null | MediaJobView }` in B's normal API wrapper. This is read-only. Photos saved before this pipeline was introduced are not silently queued by GET; explicit server `enqueueForDraft` or a new draft-bound capture/upload is needed.
- `POST /api/calls/:id/drafts/:draftId/media/choice` accepts `{ jobId, expectedDraftRevision, applyTitle?, applyDescription?, useEnhanced? }`. No `action` field. It returns saved draft/job plus `published: false`; publication still requires the final owner review.

The job projection includes original/enhanced asset IDs and same-origin preview URLs, `suggestedTitle`, `suggestedDescription`, `sourceDraftRevision`, `currentDraftRevision`, `selectedVariant`, title/description applied flags, safe error code, timestamps and evidence model IDs. Private originals/enhanced previews use `/api/assets/:id` so owner cookies work even when the public catalog host is a separate tunnel. Public storefront URLs remain B's separate catalog projection.

Both `analysisStatus` and `enhancementStatus` use `queued | running | ready | failed | interrupted | stale`. Missing job is not successful analysis. Model IDs/completion timestamps are recorded only after validated results. Analysis failure does not block the independent image-edit stage; either may succeed alone. No price, currency, stock or certification fields are inferred or written.

## Ownership, approval and persistence

Jobs bind authenticated owner, business, call, draft UUID, original asset and capture timestamp. Async completion never attaches by active UI product/recency. Replaced captures become stale and cannot be selected.

Applying a choice requires the current draft revision and no pending/frozen product proposal. Name/description can be applied only if the owner has not changed those source fields since capture (or they still equal this job's previously accepted suggestion). Price/stock edits do not invalidate visual results and are preserved. Variant selection can switch back to original; original bytes/asset are never deleted or replaced.

Owner choice and draft update occur atomically in the same SQLite DB. Media metadata lives in additive `shopcall_product_media_v1`; original/enhanced bytes use B's configured durable blob store. Generated bytes are size-bounded, decoded and checked for an allowed image format before a separate enhanced asset is recorded. No provider key, raw provider response, lease token or credential URL appears in API projections.

Select suggestions/enhanced image **before** the combined final review is frozen. Media finishing in the background never changes an already reviewed catalog snapshot. Original photo/manual text remain usable when providers fail.

## Worker and bounded cost

`npm run worker -- --loop` runs the media queue independently of the Replit publication loop, checking for another media job about every two seconds. `--once` performs one media iteration; `--run <build-job-uuid>` is publication-only.

Automatic queue is idempotent for the same draft/original/capture. At most eight new-original jobs per call and thirty per business per UTC day are eligible; further captures retain their original but record `MEDIA_LIMIT_REACHED` without model requests. Repeated queue clicks do not regenerate failed/interrupted jobs.

Each stage persists intent before its provider call. An expired running lease becomes `interrupted`, not an automatic paid retry. An independent stage that was never attempted may still run. Unknown image-edit outcomes must be reconciled rather than silently repeated. No automatic model fallback is implied by a failure status.

## Provider configuration and actual verification

Server-only `AI_GATEWAY_API_KEY` is preferred for a long-running local worker; linked-project `VERCEL_OIDC_TOKEN` is also accepted. OIDC credentials expire and need refresh through the platform; never put either credential in browser code, committed files or docs. Model overrides are `SHOPCALL_VISION_MODEL` and `SHOPCALL_IMAGE_MODEL`.

Code defaults are `google/gemini-2.5-flash-lite` for vision and `google/gemini-2.5-flash-image` for editing. The current demo explicitly selects **`openai/gpt-image-1-mini`** for editing. Google image editing was rejected for the current account/plan during verification; that route was not reported as a successful generation.

Parent verified actual strict vision output and an actual successful synthetic image edit through the selected OpenAI route. This proves provider integration, not acceptance on the merchant's real photograph. Real merchant product fidelity and owner approval remain unverified until the live photo is processed and reviewed. Synthetic proof is not real inventory or a published storefront.

Eight backend tests pass for immediate/idempotent enqueue, original preservation, explicit variant/text selection, owner isolation, stale capture/revision/proposal rejection, independent stage failure, no uncertain-attempt replay, actual DB restart persistence, and per-call/day limits. Provider calls in these tests are mocks; they generate no paid output.
